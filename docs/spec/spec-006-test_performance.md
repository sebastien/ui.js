# ui.js Core Performance Test Suite Specification

## 1. Objectives & Baseline Establishment
The primary goal of this test suite is to continuously measure the performance of `ui.js` components, ensuring that its granular rendering and reactive primitives remain highly efficient.

* **File Structure**:
  * `tests/bench-core_performance.html`: The test harness. This loads the core `ui.js` primitives and a heavy DOM benchmarking component.
  * `tests/bench-core_performance.js`: The Playwright runner. This orchestrates the lab environment, drives the browser, calculates statistics, and integrates with CI.
* **Baseline Capture**: Before beginning optimization or establishing new features, capture an initial snapshot of current performance across all metrics to serve as a reference point. The first successful run will generate a `tests/perf-baseline.json` file loging hardware constraints, OS, Node version, and the baseline metric values.
* **Environment Consistency**: Fully document all testing conditions, including device specifications, browser versions, and network settings, to ensure tests can be replicated consistently across releases.

## 2. Testing Methodology
The suite utilizes a dual-pronged approach to capture both controlled and real-world performance data:

* **Lab Testing**: `bench-core_performance.js` utilizes Playwright to launch multiple browser contexts. It explicitly throttles the CPU (e.g., 4x slowdown) and Network (e.g., Fast 3G) via the Chrome DevTools Protocol (CDP) to create standardized, repeatable testing environments.
* **Field Testing (RUM)**: The `bench-core_performance.html` file embeds a simulated Real User Monitoring (RUM) script using `PerformanceObserver`. It captures web vitals natively from the page context exactly as it would in production, passing the data back to the Playwright runner.

## 3. Specific Rendering Tests & Key Metrics
The HTML harness executes specific stress-test scenarios, capturing metrics to ensure granular rendering remains highly efficient:

### Rendering Tests
1. **Initial Mount (Heavy DOM Tree)**: Render a massive `ui.js` component tree (10,000+ nested nodes, like a complex data grid) to measure the raw cost of `ui.js` creating elements and attaching bindings.
2. **Granular Update (Localized Reactive Change)**: Trigger a localized state change deep inside the massive tree to prove `ui.js` does not over-render the surrounding nodes.
3. **Bulk Structural Update (List Reconciliation)**: Reverse, sort, or heavily filter a list of 10,000 components to test DOM node recycling.
4. **High-Frequency Updates (Animation Loop)**: Modify a reactive property mapped to 1,000 nodes inside a `requestAnimationFrame` loop to test main-thread availability under stress.
5. **Teardown / Memory Leak (Mount/Unmount Cycles)**: Mount the massive tree, entirely unmount it, and repeat 10 times to verify garbage collection.

### Key Metrics & Performance Budgets
**Web Vitals (Performance Budgets):**
* `lcp_ms: number` - Largest Contentful Paint (Budget: `< 2.5 seconds`).
* `inp_ms: number` - Interaction to Next Paint (Budget: `< 200 milliseconds`).
* `cls_score: number` - Cumulative Layout Shift.

**Micro-Benchmarks & Resource Metrics:**
* `mount_time_ms: number` - Raw JS execution time for the initial tree creation.
* `update_granular_ms: number` - Execution time for a single reactive state change.
* `update_bulk_ms: number` - Execution time for list reconciliation.
* `unmount_time_ms: number` - Execution time for DOM teardown and listener unbinding.
* `normalized_update_time_ms: number` - `update_bulk_ms` divided by the number of mutated nodes, to track per-node efficiency.
* `fps_avg: number` - Average frames per second maintained during the high-frequency test.
* `memory_retained_kb: number` - Heap size difference from the start to the end of the Teardown test (Should be ~0).

## 4. Reporting & Data Analysis
Reports generated by the suite must contextualize the data rather than relying on simple averages:

* **Percentile Analysis**: The test runs multiple times ($N$ runs). It collects arrays of all timings and calculates the **75th (P75)** and **95th (P95)** percentiles to reveal worst-case user experiences and significant variability.
* **Data Segmentation**: The Playwright script runs tests against predefined profiles (e.g., "High-End Desktop", "Low-Memory Mobile"). Reports segment metrics by device profile.
* **Discrepancy Analysis**: The script cross-references the native CDP/Lab timings against the simulated RUM timings emitted by the HTML page, explicitly highlighting discrepancies in the final report.

## 5. Automation & Iterative Lifecycle
Benchmarking is implemented as an ongoing process:

* **Continuous Integration (CI)**: Automated tools will track key metrics. The script outputs a failure (`process.exit(1)`) if the P75 of `lcp_ms` exceeds 2500ms or the P75 of `inp_ms` exceeds 200ms.
* **Iterative Trends**: The script appends the latest run's percentiles to a trend file (e.g., `artifacts/perf-trend.csv`), allowing the team to graph performance over time and analyze trends to find bottlenecks.
* **Early Integration**: Performance testing is integrated into the design phase, allowing the team to prototype with code-backed components and identify bottlenecks before heavy development begins.

## 6. Documentation
All benchmarking insights, testing conditions, and budget alerts must be heavily documented and communicated:
* Test scripts (`.js` and `.html`) contain extensive JSDoc comment blocks.
* Exact throttling multipliers and device assumptions are clearly stated.
* Reporting output includes a legend explaining how to interpret the metrics and the discrepancy between Lab and Field data.
